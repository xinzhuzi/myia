# 原生作业配置布局与取消优先级（实施57）

本轮只读取冻结4.1.15(270135)文件及既有Ghidra导出，执行自有Apple ARM64夹具；没有操作微信或调试器，没有原生接线、发送、安装或部署。A7及实施20～24、55仍开放。

## 配置不再只有opaque声明

新增`newsendmsg_job_config_4115.hpp`为既有`JobConfig`前置声明提供0x38字节、8字节对齐的研究定义：

| 偏移 | 已证明的布局与行为 |
|---|---|
| +0x00 | 24字节libc++ string，复制请求配置自己的名称，不使用组名称替换 |
| +0x18 | 8字节值，为零时继承外层group+0x120；此前已追到执行器来源 |
| +0x20 | 8字节值，为零时继承group+0x128；本组件保留原始机器字 |
| +0x28 | 8字节值，为零时继承group+0x130；本组件保留原始机器字 |
| +0x30 | 32位值，恰为-1时继承group+0x138，其他负值保持 |
| +0x34 | 32位flags，恰为0x80000000时继承group+0x13c；其他含最高位的显式值保持 |

`0x66846b8`读取x1配置、逐项补齐后，经`0x667ddf8 → 0x6681744 → 0x6681860 → 0x667e0e4`构造作业。`0x667e2d8/0x667e2dc`将配置+0x18和+0x28的两个16字节块复制到job+0xf8/+0x108；名称另行复制到job+0xe0。因此复制范围覆盖至flags+0x34，没有额外的隐式shared引用获取。机器字代表的对象仍须外部保证身份与存活，不能因结构大小符合就声称运行时就绪。

## 登记、延迟启动与取消是独立条件

新增`resolve_job_launch`只对自有快照计算配置与分支，不读取真实group或调用原生函数：

- 外层group+0x140的bit1或已补齐flags的bit1置位，跳过`0x6682d18`的登记步骤。
- 登记步骤之后，`0x6684a48`仍调用组取消查询`0x6682d08`。已取消时，优先调用Job虚槽+0x18（`0x667e8cc`），即使配置flags=3也一样。
- 组未取消时，flags bit0置位才跳过自动启动；否则调用Job虚槽+0x10（`0x667e734`）。不登记与延迟启动不能合并理解成“不受取消”。

这些步骤不构成同一原子动作。`JobGroupConfigSnapshot`明确是自有表示，不是原生组内存布局；快照中的cancelled=false不能保证后续实际启动时仍未取消，也不能证明group没有外部调用者。因此本轮不采用“设置flags=3即可解决全部取消问题”的方案，不以配置值代替组隔离、线程与释放合同。

## 启动前取消的清理限制仍保留

已重新定点核验：启动先写job+0x140，随后创建core、提交初次resume；取消可根据该标志提交已启动handler。`0x668082c`在core状态3且正文未进入时会发布作业完成；该发布不等于参数清理。core状态0取消分支`0x6674204`写3后直接返回，后来的`0x66761cc`见3会跳过恢复。正常兜底清理器的调用/清零在`0x6679950/0x6679954`，不能只凭状态3推定它必然经过。

本轮未证明原生调用方实际形成这一交错，也未证明线上泄漏。实施55仍需关闭原生外部/组取消的顺序与可达性、最终清理、真实线程和整体排空；禁止手工执行原生清理器强迫释放。
