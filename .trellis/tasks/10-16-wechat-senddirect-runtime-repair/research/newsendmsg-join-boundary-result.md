# 原生等待与最终回调释放边界（2026-10-17，实施52）

本轮只读取冻结4.1.15 ARM64文件及既有Ghidra工程，编译执行自有C++夹具。没有操作微信、附加调试器、执行原生函数或发送。账号安全停止约束保持。A7及实施20～24未完成，不能部署直发适配器。

## 已明确的资源清理合同

1. `0x667e0e4`构造时在`job+0xb8`创建promise pair，再在`0x667e214`将相同state/control pair复制到`job+0xc8`。等待方与发布方使用同一共享状态，不是两个独立完成信号。
2. `0x667fc38`先在`0x667fc94`通过promise发布零值结果，再在`0x667fcb4`派发关联通知，最后于`0x667fcd0`调用非空的最终用户function。发布状态、结果读取与最终回调返回之间不存在此函数提供的额外排空屏障。
3. 普通线程路线`0x66810c0 → 0x2c620c8 → 0x666a844`仅等待`state+0x9c`不再为零，处理状态2的类型化异常后返回`state+0x90`容器。类型getter核对冻结名称`_c7a25de5`，返回容器+8；等待调用者读取32位值。此等待没有另读最终function的销毁状态。
4. 协程路线`0x6680d54 → 0x6674d5c`中，状态getter`0x6668c3c`只读取同一`state+0x9c`；已就绪分支`0x667505c`直接返回零。这里只证明该分支，未把pending/resume/cancel整条协程合同视为完成。
5. `0x667fd04`通知派发具有直接调用和执行器虚槽+0x10两条路线；后者复制接收方拥有信息及参数后提交function。完成入口调用通知派发返回，不足以证明排队接收方已经执行或销毁；具体执行器排空仍需独立证明。

## 析构补证

从dyld链独立解码`0x9fb2c20`虚表的两个析构槽，得到`0x667e718 → 0x667f128`及`0x667e71c → 0x667f128 → sized delete(0x158)`。原生析构函数分别处理：

- `job+0x148`可选对象、`job+0x118`正文function及其存储；
- `job+0x120/+0x138`最终function，按内联/堆调用虚槽+0x20/+0x28；
- `job+0xd0/+0xc0/+0xb0`控制块strong计数递减及最后引用时的虚析构/weak释放；
- `job+0xa0`weak控制块和两处基类清理。

因此，最终function调用返回也不等于它保存在job内的捕获已经销毁。析构顺序已定位，但最后一个原生job拥有者何时释放、基类内部清理及所有排队接收方何时消失，仍未证明。禁止手工调用析构或将本结果当成模块卸载许可。

## 对适配器的实际要求

适配器必须分别保持作业、网络请求及回调共享状态的生命期。禁止在join返回、完成标志变化、回调进入或回调返回时直接释放服务/代码/全部捕获；作业取消与请求取消仍须分开处理。不得令job中保存的完成function反向强持有同一job而形成自身循环。只有对所有在途请求、最终function、排队通知和引用释放分别获得证据后，才能定义完整排空。

该合同已加入design；未用未知线程/group/config实现原生接线，产品拒绝门保持。研究fixture本身不提供加载器或调用地址。
