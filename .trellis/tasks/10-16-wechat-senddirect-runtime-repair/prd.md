# 微信直发运行入口与4.1.15适配修复

## Goal
把已确认的事故原因落实到产品代码：健康检查和演练不得隐式附加微信；已证伪的直发配方不得再执行；正确的缓冲区接口有可运行的离线实现和回归证据。任意正文真正直发仍需完成适配与独立终验。

## Background
- senddirect.py 的 doctor 默认调用 execute_send(dry_run=True)，会实际启动 LLDB，配置门开启后健康轮询能反复附加。
- 4.1.15 原生适配把 x4 输出缓冲区错认作 Task，并把 protobuf 栈对象覆盖成 AutoBuffer；已发生崩溃。
- 产品旧配方 send_entry=0x83e394 的捕获模板路线未实现任意正文直发。返回码、任务入队和 HTTP 200 均不能替代真实回执。

## Requirements
- R1 doctor 与 send_direct --dry-run 只读磁盘；不得启动调试器、布断点、触发 UI、发送消息。
- R2 当前 4.1.15 已知失效配方在附加前拒绝执行，给出具体原因；配置开关和旧授权不构成单次调试授权。
- R3 提供独立的4.1.15输出缓冲区写入模块，只使用已核验的原生长度/指针辅助函数，不写 protobuf 布局、不替换 Task 指针、不改代码；故障不得报告发送成功。
- R4 离线回归使用假进程/内存和留存二进制；不附加、不操作微信、不发送、不装机未经验收的原生适配。
- R5 无 Git/worktree、无归档、无删除历史实验；分小步编辑。用户已明确要求按报告推进修复，无需再申请实施许可。
- R6 保护修复经验证后同步到本机独立桥及桌面Python入口，先备份；不升级其余依赖、不改签名App资源、不装机未经验证的原生适配。
- R7 按用户要求纠正实际生效的版本JSON：核验当前安装包身份，失效原生配方不得继续填作可执行值；不以版本标签、旧版偏移或离线检查代替原生适配验收。

- [x] A1 开门状态下重复 doctor / dry-run，调试器与 UI 调用计数为零；磁盘缺失/变更给出正确结果。
- [x] A2 已失效4.1.15配方在产生运行工件/启动调试器前拒绝，且不留下发送占位。
- [x] A3 缓冲区实现处理中文、长文、连续调用和故障；假内存验证输出内容/长度及保护区域。

- [x] A5 静态追踪明确能继续的原生调用合同；不能证明的所有权或签名不生成运行配方。
